Why the Wi-Fi looks fine
after the outage

How RadioChron’s local flight recorder, honest evidence states and one deterministic classifier keep the black box — so cause semantics do not drift across Desktop, MCP, Agent and Node.

Every Wi-Fi engineer has had this conversation. Someone says the network dropped for two minutes at 10:14. You open the laptop at 10:21. Signal bars are full, the gateway answers, DNS resolves, speed test is fine. You have nothing. The link healed itself and took the evidence with it.

RadioChron exists for that gap. It is a local-first Wi-Fi flight recorder: a small Rust core plus a set of surfaces (Desktop, MCP, always-on agent, Node bindings, fleet inventory, an ESP-IDF adapter) that record what the link was doing before the fault, classify the fault with one deterministic ruleset, and say plainly what they could not observe. The positioning line is the whole design brief: know why Wi-Fi failed — even after it recovered.

This article is about the problem, the model RadioChron uses to attack it, and the specific engineering decision that holds the product together: one incident model, many surfaces.

1. The recovered-link paradox

Wi-Fi outages are short. Most of them are seconds to a couple of minutes: a roam that took too long, a DHCP renewal that stalled, a resolver that stopped answering, a driver that reset the adapter. By the time a human is looking at a diagnostic tool, the state has changed. Not slightly changed — completely changed. The BSSID is different, the RSSI is different, the DHCP lease is fresh, the DNS cache is warm.

The paradox is that the system which recovered is the same system you are asking to explain the failure, and it has no memory of it. Modern operating systems are optimised to make the link healthy again, not to preserve a forensic record of how it became unhealthy. Recovery is destructive.

So the engineer falls back on inference. “It was probably the AP.” “It was probably DNS.” “Have you tried a network reset?” Every one of these is a guess wearing the clothes of a diagnosis, and every one of them costs a real ticket, a real truck roll, or a real afternoon of a developer’s time. The cost is not that the guess is wrong; the cost is that nobody can tell whether it was right.

2. What breaks in conventional tooling

Conventional Wi-Fi diagnostics are snapshot tools. They answer the question “what is the state right now?” with varying degrees of precision. That is a fine question at the moment of failure and a useless one seven minutes later.

ping and traceroute

Ping tells you whether an ICMP echo made it to a target and back now. It cannot tell you that the gateway was fine and the resolver was dead. It cannot tell you that the client was associated the whole time but had no IP for forty seconds. It collapses seven distinct failure stages into one boolean, and it only reports the boolean while you are watching.

OS Settings and the tray icon

The OS network UI is optimised for reassurance. “Connected, secured” is a statement about 802.11 association and key exchange, and the association layer is frequently the layer that is fine. A client can be perfectly associated to an AP whose uplink has failed, whose DHCP server is exhausted, or whose advertised resolver is dead. The UI will show the full bar set. It is not lying; it is answering a narrower question than the one you asked.

“Network reset”

The nuclear option: forget all networks, reinstall adapters, reboot. It is offered because it sometimes works, and it sometimes works because it happens to coincide with the underlying fault clearing. It is also an evidence-destruction event. If the cause was a driver reset loop, a sticky client that would not roam, or an AP with a failing key exchange, “network reset” removes the last traces of it and guarantees a repeat.

Windows Event Viewer

Windows actually keeps a good record. The WLAN-AutoConfig operational log carries connect, disconnect and failure events with numeric event IDs and reason codes, and each connection attempt is tagged with a ConnectionId. The problem is not that the data is missing; it is that the tooling people use to read it is built around localized message strings. Parsing “The network connection was disconnected because…” works on an English machine with one Windows build and breaks on the next. RadioChron reads the numeric IDs and reason codes, and uses ConnectionId continuity to tell a roam within one connection from a genuine fault that started a new one.

The common thread: none of these tools has a before. They have a now, and sometimes a badly-parsed log. Neither is a timeline.

3. Flight-recorder model versus snapshot diagnostics

A flight recorder does not wait for you to ask. It keeps a bounded ring of recent observations at all times, and when something interesting happens it freezes that ring plus a short post-window and hands it over for analysis. That is exactly what the flight module in the radiochron core does, and it does it without any I/O.

The sample

One tick of observation is a FlightSample: monotonic timestamp, optional wall clock, interface id, association state, SSID and BSSID (identity fields the host may redact by policy), RSSI, rx/tx rates, channel, the connectivity stage that failed on this tick if any, and a collector_healthy flag. Cheap enough to take every second or two forever.

The policy

Retention is bounded by a host-supplied FlightPolicy. The defaults in core are deliberately conservative: a bounded sample ring, a short maximum age, a post-window after a trigger, a cooldown so a flapping link cannot generate a hundred incidents, and a signal-drop threshold. Hosts can tighten these; they cannot make the recorder unbounded.

The triggers

The recorder watches consecutive samples and opens a post-window on any of:

  • AssociationLost — associated on the previous tick, not associated now.
  • BssidRoam — associated, but the BSSID changed.
  • SignalDrop — RSSI fell by at least the policy threshold between ticks.
  • ConnectivityStageFail — a stage in the connectivity ladder failed.
  • CollectorGap — the collector itself reported unhealthy. Losing the ability to observe is itself an event worth recording.
  • Manual — an operator or host policy asked for a window.

When the post-window elapses, the recorder emits a FlightWindow: the trigger, the trigger timestamp, and every sample still in the ring — which means the pre-trigger baseline is included. The host (in practice radiochron-agent) spools it. The core never sleeps, polls or touches a filesystem; it is a state machine you feed samples to.

// Host loop, simplified
let decision = recorder.observe(sample);
if let Some(window) = recorder.take_closed_window() {
    spool.write(window);          // agent's job
    evidence.flight_window = ...; // then classify
}

Contrast this with a snapshot tool: the snapshot tool has one sample, taken at the wrong time, with no trigger context. The flight recorder has the sample from the wrong time and the window before it and after it, and it knows which trigger opened the capture.

4. Evidence honesty: available, unavailable, failed, not_requested

Here is a quiet bug that lives in most diagnostic tools: the absence of a signal is treated as a good signal. The history collector threw an exception, so the history list is empty, so “no reconnect loops detected.” The connectivity probe was never run, so “no stage failures.” The tool reports green because it did not look.

RadioChron’s incident model refuses to do this. Every input to the classifier is wrapped in EvidenceSection<T>, which has exactly four states:

  • available — the section was collected; here is the data.
  • unavailable — the section was requested but cannot exist on this host, with a reason. Windows WLAN history on Linux, for example.
  • failed — the collector tried and broke, with an error class and message.
  • not_requested — the surface did not attempt this section. This is the default; a surface has to opt in.

The classifier treats these differently and the report says so. Two hard rules sit at the top of incident::classify:

  • If no sections were requested, the assessment is unknown with the limitation that no evidence sections were requested.
  • If sections were requested but none came back available, the assessment is unknown with the limitation that requested sections were unavailable or failed.

Below that, every unavailable or failed section becomes an evidence gap in the report. And the “looks healthy” check is asymmetric on purpose: a not_requested section does not block a healthy verdict, but a failed section does. If the history collector crashed, the classifier will not call the link healthy on the strength of the sections that survived.

This is the line in ADR 001: unknown or missing evidence must not be treated as healthy. It sounds like a small thing. It is the difference between a tool that tells you what it knows and a tool that tells you what you want to hear.

The evidence sections currently include wifi_status, wifi_analysis, connectivity, history, chronicle, flight_window, adapter and ble. Adapter fingerprints additionally carry their own evidence quality (measured, reported or unknown), because a driver version read from the OS is not the same grade of fact as a value the collector measured itself.

5. Deterministic classification, and why one classifier matters

The classifier is a pure function: classify(&IncidentEvidence) → IncidentReport. No I/O, no clock, no randomness, no model weights. Same evidence in, byte-identical report out, on Windows, Linux, macOS, or an ESP32 (the module is alloc-only). That property is not an implementation detail; it is what makes the rest of the product possible.

What it produces

An IncidentReport carries a schema version, the observation timestamp, an assessment (healthy, degraded, incident, unknown), an ordered list of causes, the evidence references those causes cite, the gaps, action hints, and free-text limitations. Each cause has a kind, a confidence, a one-line summary, and evidence refs pointing at the specific thing that justified it: a Windows event record id, a connectivity stage name, an analysis finding id, a chronicle event, or a flight sample sequence number.

The cause vocabulary follows the connectivity ladder plus the RF layer underneath it:

rf_weak_signal          rf_contention           roaming_transition
association_failure     authentication_failure  credential_mismatch
access_point_key_exchange
dhcp_or_ip_assignment   gateway_reachability    dns_failure
tcp_service_failure     tls_failure             internet_upstream_failure
collector_gap           non_wifi_failure        unknown

How it rules

Rules are table-driven and boring by design:

  • History finding reconnect_loop → association_failure, high confidence — Windows WLAN history shows a reconnect loop across ConnectionId changes.
  • History finding credential_mismatch → credential_mismatch, high; key-exchange failures map to access_point_key_exchange.
  • Connectivity failed stage dns → dns_failure, high — “DNS resolution failed while lower stages passed.” Each stage name maps one-to-one onto a cause kind.
  • Analysis finding weak_signal_link → rf_weak_signal, medium. Sticky-client roam candidates map to roaming_transition at low confidence — a plausible contributor, not a proven cause.
  • Status with interfaces reported but none associated → association_failure, medium. Status with no interfaces at all → collector_gap, not a Wi-Fi verdict.

Causes are deduplicated by kind and sorted by a fixed priority that runs from the most actionable (credential mismatch, AP key exchange) down through the ladder to RF conditions, collector gaps and unknown. Assessment is then derived: any ladder-stage or auth cause → incident; only RF, roaming or collector-gap causes → degraded; nothing matched and the evidence actually looked clean → healthy; otherwise unknown.

Why one, and only one

Without a shared model, RadioChron was heading where every multi-surface product heads. The MCP server had its own diagnose_incident orchestration. The Electron app built its own Windows timeline — and classified WLAN events by matching localized message strings. The core already had a better Windows history detector reading numeric event IDs and ConnectionId continuity. Three surfaces, three slightly different opinions about what a “reconnect loop” is.

That drift is fatal for a diagnostics product. If the Desktop says roaming_transition and the MCP tool says association_failure for the same sixty seconds of the same machine, the user is right to trust neither. The fix was not to synchronise three classifiers; it was to delete two of them.

Core owns the evidence shape, the report schema and the classifier. Surfaces own collection orchestration, scheduling, transport, storage and UI. MCP, Node, Agent and Desktop call the same classify over the same evidence types and may not invent parallel root-cause logic in JavaScript or MCP layers. Fixture parity tests across surfaces enforce it: the same JSON evidence must produce the same JSON report whether it went through Rust, Node or MCP.

Determinism is what makes that enforceable. You cannot write a parity fixture against a classifier that consults the clock.

6. Surfaces: orchestration without opinion

With cause logic pinned in core, each surface is free to do the thing it is actually good at.

Desktop (radiochron-electron)

The Desktop app is the timeline. It renders association history, channel environment, Bluetooth context, and closed incidents with their reports. On Windows it reads the WLAN-AutoConfig operational log by numeric event ID and reason code, threads events on ConnectionId so a roam inside one connection is not mistaken for a disconnect/reconnect fault, and passes normalised history evidence to core. It no longer parses message text. It can export an incident as a bundle. It does not classify.

MCP and CLI (radiochron-mcp, radiochron doctor)

radiochron doctor is the on-demand collector: run it when someone says “the Wi-Fi is weird,” and it requests status, analysis, connectivity, history and adapter sections, marks each one available / unavailable / failed honestly, and prints the core report. The same orchestration is exposed as an MCP tool so an assistant or automation can ask for a verdict and receive a structured IncidentReport rather than prose. The MCP layer does not add its own reasoning about causes; it returns what core said, including the gaps and limitations.

Agent (radiochron-agent)

Always-on flight recording belongs to the agent and nowhere else — because a Desktop app that is not running and an MCP server that only wakes on request cannot be black boxes. The agent drives the core FlightRecorder with periodic samples, spools each closed FlightWindow locally, and attaches the window as flight evidence when it classifies. Nothing leaves the machine unless a human exports a bundle.

Node (radiochron-js)

The npm surface exposes diagnose() and history() on top of the shared classifier. If you are building an Electron app of your own, a support tool, or a CI job that checks a test rig’s Wi-Fi before a run, you get the identical report object the Desktop shows. There is no JavaScript reimplementation of the rules to fall out of date.

The transfer format

When a report needs to move between surfaces or people, it travels as radiochron.incident_bundle.v1, a JSON document with the .rchron extension. A bundle carries the producer (surface, surface version, core version), the platform, a privacy manifest, the IncidentReport, and optionally the raw evidence sections that produced it. A bundle produced by the agent on a laptop can be opened in Desktop, replayed through classify, and must produce the same verdict — because the verdict is a function of the evidence, not of where it was computed.

7. A worked mini-timeline

Here is the kind of incident that snapshot tools cannot explain and that the flight recorder was built for. Times are relative; values illustrate the shape, not a specific customer’s data.

t-45s  associated  BSSID A  ch 36   RSSI -58   all stages ok
t-30s  associated  BSSID A  ch 36   RSSI -63   all stages ok
t-15s  associated  BSSID A  ch 36   RSSI -71   all stages ok
t-5s   associated  BSSID A  ch 36   RSSI -79   all stages ok
       ← analysis: weak_signal_link, sticky_client_roam_candidate
t0     associated  BSSID B  ch 44   RSSI -55   all stages ok
       ← trigger: BssidRoam
t+3s   associated  BSSID B  ch 44   RSSI -54   dns FAILED
t+8s   associated  BSSID B  ch 44   RSSI -54   dns FAILED
t+14s  associated  BSSID B  ch 44   RSSI -55   all stages ok
       ← recovered
t+20s  post-window closes; window spooled; cooldown

What the user experienced: video call froze for about ten seconds, then came back. What the OS showed throughout: connected, full bars. What ping 1.1.1.1 would have shown at t+3s: replies. The radio, auth, DHCP and gateway stages were fine after the roam. The resolver was not — the classic case where association looks perfect while the application outage is at DNS.

The agent hands core an IncidentEvidence with flight_window available, connectivity available with DNS failed, wifi_analysis available with the two finding ids from t−5s, wifi_status available and associated, and history marked unavailable because this host is macOS. The classifier returns, in shape:

{
  "schema_version": 1,
  "assessment": "incident",
  "causes": [
    { "kind": "dns_failure", "confidence": "high",
      "summary": "DNS resolution failed while lower stages passed" },
    { "kind": "rf_weak_signal", "confidence": "medium",
      "summary": "associated link signal is weak" },
    { "kind": "roaming_transition", "confidence": "low",
      "summary": "client appears sticky to a weaker BSS" }
  ],
  "gaps": [
    { "section": "history",
      "impact": "section unavailable: not a Windows host" }
  ],
  "limitations": [
    "Windows WLAN history was not available; reconnect loops may be under-detected"
  ]
}

Read the verdict the way the classifier built it. The assessment is incident, not degraded, because a ladder stage failed. The primary cause is DNS at high confidence. The weak signal and sticky-client behaviour are listed after it and at lower confidence: they are true, they are part of the story, but they are not the thing that froze the call. The gap and limitation are stated rather than hidden. The action hint points at the resolver, not at “reset your network.”

Now the important part: this report is identical whether the agent produced it, whether you ran radiochron doctor at t+3s, whether you called diagnose() from Node, or whether you exported the .rchron bundle and opened it in Desktop a week later. Same evidence, same function, same verdict. That is the specific task the shared model solves for RadioChron — not “better Wi-Fi analysis” in the abstract, but the guarantee that cause semantics cannot drift between the surface that recorded the incident and the surface a human reads it on.

8. Privacy: what a bundle contains and what not to share

RadioChron has no telemetry. There is no account, no upload, no phone-home, no usage analytics. The agent spools to local disk; the Desktop reads local files; the MCP server answers local requests. This website is static and renders without JavaScript. That is the natural consequence of a tool whose entire value is that the evidence is on the machine where the fault happened.

That said, a flight recorder is a surveillance device by construction, and an incident bundle is a document you might hand to a colleague, a vendor or a forum. Be deliberate about it.

  • SSIDs and BSSIDs are location data. A BSSID is a globally unique AP identifier; public wardriving databases map many of them to coordinates. Redact both before sharing outside your organisation.
  • The flight window is a movement log. A short ring of RSSI and BSSID transitions describes physically walking through a building. Treat it like one.
  • Adapter fingerprints identify hardware. Driver and firmware versions are what fleet correlation needs, and also what an attacker looking for a known-vulnerable driver needs.
  • Windows history contains ConnectionIds and event record ids that are meaningless outside the machine but can be joined against other logs from that machine.

The bundle schema makes the choice explicit. Every .rchron can carry a privacy manifest with a level and the list of fields that were redacted. A recipient can see at a glance that BSSIDs were stripped, and the classifier still works on redacted documents because it reasons over finding ids and stage names, not over identifiers. The core is MIT / Apache-2.0 — you can read the collectors and confirm what gets written.

9. Who this is for

RadioChron is not a speed test, a heat-mapper or a packet capture tool. It is for the moment after those tools have already failed you — when the link is back, the user is annoyed, and the only honest answer available is “I don’t know, it works now.”

It is for the developer whose IoT device drops off the network once a night and reconnects before anyone can attach a debugger, and who can now run the same recorder on the ESP32 and on the laptop that talks to it and get the same report schema from both.

It is for the IT engineer who fields “Wi-Fi is bad on the third floor” and wants a spool of closed incidents with roam and stage evidence instead of a request to reproduce it on demand.

It is for the support team that receives .rchron bundles from users and needs the verdict in the bundle to be the same verdict the user saw, computed by the same code, with the gaps written down.

And it is for anyone building on top: the Node binding, the MCP tool and the fleet inventory exist so that you can put RadioChron’s evidence and verdict inside your own workflow without inheriting the job of keeping a second classifier honest.

The link will recover. The question is whether anything remembers why it failed. RadioChron’s answer is a bounded ring, four evidence states, one pure function, and a bundle you control.
